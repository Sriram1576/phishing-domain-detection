  87 [Normal              ] 1. INTRODUCTION
  88 [Normal              ] 1.1 Background and Motivation
  89 [Normal              ] Most online services rely on web browsers as the primary interface for banking, shopping, and enterprise work. Attackers exploit this reliance through phishing pages that visually mimic genuine login portals. Historically, organizations guarded against these attacks by maintaining blacklists of verified malicious domains. However, modern attackers automate domain generation and use disposable cloud hosting, meaning a phishing link might only stay active for a few hours. By the time a victim reports the page and a blacklist administrator flags it, the attack has already succeeded. Machine learning approaches that only examine the text of a URL also fall short, as attackers can easily craft URLs that look clean and contain no suspicious keywords. To reliably identify these threats before they are blacklisted, we need to inspect the underlying infrastructure that supports them.
  90 [Normal              ] 1.2 Problem Statement
  91 [Normal              ] Phishing detection based purely on static rules or isolated URL strings ignores the network relationships that connect malicious operations. Attackers repeatedly reuse specific DNS nameservers, register multiple domains through the same registrar accounts, and host pages across shared IP subnets. Evaluating a URL in isolation throws away this relational context. Our goal is to model these network entities into a connected graph and use Graph Neural Networks (GNNs) to classify whether a target domain is legitimate or phishing in real time.
  92 [Normal              ] 1.3 Objectives
  93 [Normal              ] Build an automated backend pipeline that queries live DNS, WHOIS, and SSL data for any submitted URL.
  94 [Normal              ] Model these entities and their interactions as heterogeneous star graphs using NetworkX.
  95 [Normal              ] Train and fine-tune a Graph Convolutional Network in PyTorch Geometric that achieves at least 95% accuracy.
  96 [Normal              ] Keep the entire verification process under a 2 to 3 second response window so that it works seamlessly for everyday users.
  97 [Normal              ] Benchmark the GNN against baseline tabular models like Random Forest and XGBoost to evaluate the impact of graph structures.
  98 [Normal              ] Create an easy-to-use web interface backed by Flask and SQLite to display predictions, confidence scores, and historical lookups.
  99 [Normal              ] 1.4 Purpose and Scope
 100 [Normal              ] Purpose: To provide a practical, AI-driven security tool that allows individuals and system administrators to check suspicious URLs before interacting with them.
 101 [Normal              ] In Scope:
 102 [Normal              ] Collecting balanced datasets from public repositories (PhishTank, OpenPhish, Tranco/Kaggle).
 103 [Normal              ] Real-time network extraction (DNS lookups, socket-level SSL checks, WHOIS parsing).
 104 [Normal              ] Graph construction, PyG tensor conversion, and model inference.
 105 [Normal              ] Web interface with instant risk feedback and a local SQLite database for history logging.
 106 [Normal              ] Out of Scope:
 107 [Normal              ] Full-page DOM scraping and dynamic headless browser rendering.
 108 [Normal              ] Browser extensions or email client integration.
 109 [Normal              ] Distributed cloud deployment or high-throughput enterprise network gateway integration.
 110 [Normal              ] 1.5 Major Features
 111 [Normal              ] Live Feature Extraction: Gathers lexical, DNS, WHOIS, and SSL attributes on the fly when a link is submitted.
 112 [Normal              ] Graph Modeling: Represents domains, IP addresses, nameservers, and registrars as connected nodes rather than flat table rows.
 113 [Normal              ] History Dashboard: Retains an audit trail of past queries and risk levels in a local SQLite database for easy reference.
 114 [Normal              ] 2. LITERATURE REVIEW
 115 [Normal              ] A review of classical heuristic, machine learning, and emerging graph-based detection approaches reveals key performance patterns and architectural limitations across current domain classification methods.
 116 [Normal              ] 2.1 Relevant Existing Work
 117 [Normal              ] Prior research in phishing detection spans four primary technical paradigms: lexical URL heuristics, network infrastructure analysis, visual page inspection, and graph-based representation learning.
 118 [Normal              ] 1. Lexical and Natural Language Processing Heuristics
 119 [Normal              ] Early automated approaches focused on extracting features directly from the raw text of the URL without making external network calls.
 120 [Normal              ] Marchal et al. (2014) introduced PhishStorm, a streaming analytics pipeline designed to evaluate lexical features at wire speed. The authors demonstrated that character distributions, token positioning, and vocabulary anomalies can differentiate malicious links in high-throughput traffic.
 121 [Normal              ] 2. DNS Metadata and Hosting Infrastructure Mining
 122 [Normal              ] Recognizing that attackers can craft URLs that look clean and unthreatening, researchers turned to analyzing the network infrastructure supporting the domain.
 123 [Normal              ] Al-Ahmadi (2020) examined passive DNS traffic logs using XGBoost to detect malicious domains. The study established that hosting anomalies—such as abnormally short Time-to-Live (TTL) values, rapid IP churn, and associations with low-reputation Autonomous System Numbers (ASNs)—are strong indicators of botnet Command-and-Control (C2) and credential-harvesting servers.
 124 [Normal              ] 3. Visual and DOM-Based Inspection
 125 [Normal              ] To catch deceptive landing pages that use legitimate-looking domains or clean subdomains, several systems evaluate the rendered webpage content.
 126 [Normal              ] Rao and Pais (2020) developed CatchPhish, a multi-modal framework that pairs URL text classification with computer vision. The system uses a headless browser to capture full-page screenshots and render the Document Object Model (DOM), applying Convolutional Neural Networks (CNNs) to detect visual impersonation of trusted brand logos and login interfaces.
 127 [Normal              ] 2.2 Comparative Analysis
 130 [Normal              ] 2.3 Limitations
 131 [List Paragraph      ] Blacklists are always playing catch-up: Services like Google Safe Browsing or PhishTank only work after someone has already been targeted, reported the link, and had it verified. Because attackers can spin up new domains automatically and discard them a few hours later, these lists consistently miss zero-hour attacks during the most dangerous window.
 132 [List Paragraph      ] URL text alone is too easy to disguise: Simple lexical checks—like counting hyphens, calculating string randomness, or hunting for words like "login" are trivial to bypass. Attackers can register clean, normal-looking domain names or hide the spoofed brand name deeper inside the URL path where basic filters fail to flag it.
 133 [List Paragraph      ] Rendering full webpages is way too slow: Tools that open links in headless browsers to scan HTML structure or capture page screenshots take anywhere from 5 to 15 seconds per check. That makes real-time protection painful for users, and sophisticated phishing pages can easily detect automated bots and serve them blank or harmless pages instead.
 134 [Normal              ] 2.4 Relevance to the Proposed Project
 135 [Normal              ] The literature directly shaped the architectural decisions, feature choices, and trade-offs in our proposed system:
 136 [Normal              ] 1. Ingestion of String-Level Diagnostics
 137 [Normal              ] The lexical methods established by Marchal et al. and Sahingoz et al. informed the initial feature set assigned to our central URL node. We incorporated character-level Shannon entropy, special character frequencies, and digit ratios into the feature vector. However, observing how easily string-only classifiers are evaded by clean domain names led us to treat lexical attributes merely as one component of a broader node profile, rather than relying on them as the sole decision source.
 138 [Normal              ] 2. Relational Infrastructure Modeling
 139 [Normal              ] Al-Ahmadi’s findings on DNS traffic directly influenced our network extraction pipeline. Instead of evaluating a domain in isolation, our backend actively queries live A-records, authoritative nameservers, and WHOIS registration age. Crucially, rather than flattening these network attributes into a standard tabular row, our project maps them into distinct physical nodes, allowing the model to inspect the hosting environment surrounding the domain.
 140 [Normal              ] 3. Avoiding Content-Rendering Bottlenecks
 141 [Normal              ] While visual inspection frameworks like CatchPhish achieve solid detection rates, their multi-second rendering overhead and vulnerability to anti-bot cloaking scripts make them unsuitable for instant checks. By reviewing these trade-offs, we deliberately scoped our system around socket-level metadata (DNS, WHOIS, SSL handshakes). This allows our system to capture structural malice while maintaining a sub-3-second response time.
 142 [Normal              ] 3. SYSTEM ANALYSIS
 143 [Normal              ] 3.1 Existing Systems & Proposed System
 144 [Normal              ] 3.1.1 Existing Systems
 145 [Normal              ] Most desktop security products and browser plugins check incoming links against public blocklists like Google Safe Browsing or Spamhaus. When an unknown URL appears, they fall back to basic lexical checks (such as measuring the length of the string, counting hyphens, or flagging words like "login" and "verify").
 146 [Normal              ] These approaches have two primary flaws:
 147 [Normal              ] Blocklists have a noticeable lag time between when an attack launches and when it gets cataloged.
 148 [Normal              ] Attackers can easily circumvent lexical models by picking clean-looking domain names or using free subdomains that look completely harmless.
 149 [Normal              ] 3.1.2 Proposed System
 150 [Normal              ] Our approach shifts the focus from what the URL looks like to what it is connected to. When a user enters a link, the system gathers its network footprint in real time—who registered it, how old it is, what IP it points to, and which nameservers manage it. By passing this network structure through a Graph Convolutional Network, the system can spot malicious patterns even if the URL string itself looks completely legitimate.
 151 [Normal              ] 3.2 Requirements Specification
 152 [Normal              ] 3.2.1 Functional Requirements
 153 [Normal              ] Input Handling: The web interface must accept a URL string, check that it follows valid web syntax, and strip away protocol headers to isolate the domain.
 154 [Normal              ] Live Extraction: The backend must query DNS servers for A and NS records, fetch WHOIS creation and expiry dates, and establish an SSL handshake to inspect certificate validity.
 155 [Normal              ] Graph Generation: The system must construct an in-memory graph connecting the domain to its resolved IP, its nameserver, and its registrar using NetworkX.
 156 [Normal              ] PyG Formatting: The system must convert the NetworkX graph into an edge list tensor and node feature tensor suitable for PyTorch Geometric.
 157 [Normal              ] Classification: The trained GCN model must evaluate the graph tensors and output whether the link is Legitimate or Phishing, alongside a confidence percentage.
 158 [Normal              ] 3.2.2 Non-Functional Requirements
 159 [Normal              ] Latency: Total processing time—from clicking "Detect" to seeing the result must stay between 2 and 3 seconds under normal network conditions.
 160 [Normal              ] Accuracy: The trained model must maintain an overall detection accuracy of at least 95% on unseen test data.
 161 [Normal              ] Fault Tolerance: If an external WHOIS or DNS query times out, the feature extractor must insert neutral fallback values rather than throwing an unhandled exception.
 162 [Normal              ] Security: All user input must be sanitized to guard against cross-site scripting (XSS), and database queries must use parameterized calls to prevent SQL injection.
 163 [Normal              ] Portability: The entire system must run on standard Windows or Linux setups using Python 3.11+ without needing specialized proprietary drivers.

 249 [Normal              ] 4.2.1 Process Specifications(Algorithms/Pseudocode)
 250 [Normal              ] Algorithm 1: Real-Time Dynamic Heterogeneous Graph Construction
 251 [Normal              ] Algorithm: BuildHeterogeneousDomainGraph
 252 [Normal              ] Input: Feature dictionary F containing {fqdn, ip, ns, registrar, lexical_vector, age, ttl, ssl_valid}
 253 [Normal              ] Output: PyTorch Geometric Data object D = (X, E)
 254 [Normal              ] 1:  Initialize an empty directed graph G using NetworkX: G ← Graph()
 255 [Normal              ] 2:  Define Node IDs:
 256 [Normal              ] 3:      ID_URL ← 0
 257 [Normal              ] 4:      ID_IP  ← 1
 258 [Normal              ] 5:      ID_NS  ← 2
 259 [Normal              ] 6:      ID_REG ← 3
 260 [Normal              ] 7:
 261 [Normal              ] 8:  Construct Feature Vectors:
 262 [Normal              ] 9:      X_url ← Normalize([F.length, F.entropy, F.digit_ratio, F.special_char_count])
 263 [Normal              ] 10:     X_ip  ← Normalize([Hash(F.ip) % 1000, F.ttl, ConvertASN(F.ip)])
 264 [Normal              ] 11:     X_ns  ← Normalize([Hash(F.ns) % 1000, F.ttl])
 265 [Normal              ] 12:     X_reg ← Normalize([F.age, F.ssl_valid, Hash(F.registrar) % 1000])
 266 [Normal              ] 13:
 267 [Normal              ] 14:     Pad vectors X_url, X_ip, X_ns, X_reg with one-hot entity type indicators to uniform dimension d = 16
 268 [Normal              ] 15:
 269 [Normal              ] 16: Add nodes with attributes to G:
 270 [Normal              ] 17:     G.add_node(ID_URL, x=X_url)
 271 [Normal              ] 18:     G.add_node(ID_IP,  x=X_ip)
 272 [Normal              ] 19:     G.add_node(ID_NS,  x=X_ns)
 273 [Normal              ] 20:     G.add_node(ID_REG, x=X_reg)
 274 [Normal              ] 21:
 275 [Normal              ] 22: Add directed relational edges:
 276 [Normal              ] 23:     G.add_edge(ID_URL, ID_IP,  relation="RESOLVES_TO")
 277 [Normal              ] 24:     G.add_edge(ID_URL, ID_NS,  relation="DELEGATED_TO")
 278 [Normal              ] 25:     G.add_edge(ID_URL, ID_REG, relation="REGISTERED_BY")
 279 [Normal              ] Algorithm 2: GCN Forward Propagation and Inference
 280 [Normal              ] Algorithm: GCNForwardInference
 281 [Normal              ] Input: Pre-trained weights {W1, W2, W_fc, B1, B2, B_fc}, Input graph D = (X, E)
 282 [Normal              ] Output: Predicted Class C ∈ {Legitimate, Phishing}, Calibrated Probability P
 283 [Normal              ] 1:  Extract node features X ∈ R^(4 x 16) and edge index E ∈ R^(2 x 10)
 284 [Normal              ] 2:  Compute augmented degree matrix D_hat where D_hat(i, i) = 1 + Sum_j (E(i, j))
 285 [Normal              ] 3:  Compute normalized symmetric adjacency matrix:
 286 [Normal              ] 4:      A_norm = D_hat^(-1/2) * A_hat * D_hat^(-1/2)
 287 [Normal              ] 5:
 288 [Normal              ] 6:  // Layer 1: Graph Convolution & Feature Transformation
 289 [Normal              ] 7:  H1 = A_norm * X * W1
 290 [Normal              ] 8:  H1 = BatchNormalization(H1)
 291 [Normal              ] 9:  H1 = ReLU(H1)
 292 [Normal              ] 10:
 293 [Normal              ] 11: // Layer 2: Relational Aggregation
 294 [Normal              ] 12: H2 = A_norm * H1 * W2
 295 [Normal              ] 13: H2 = BatchNormalization(H2)
 296 [Normal              ] 14: H2 = ReLU(H2)
 297 [Normal              ] 15:
 298 [Normal              ] 16: // Global Readout: Graph-Level Summary Vector
 299 [Normal              ] 17: h_graph = (1 / 4) * Sum_{i=0}^{3} (H2[i, :])   // Global Mean Pooling
 300 [Normal              ] 18:
 301 [Normal              ] 19: // Linear Projection Head & Softmax
 302 [Normal              ] 20: Z = h_graph * W_fc + B_fc                       // Logits in R^2
 303 [Normal              ] 21: Probabilities = Softmax(Z)                      // [P(Legitimate), P(Phishing)]
 304 [Normal              ] 22:
 305 [Normal              ] 23: IF Probabilities[1] >= 0.50 THEN
 306 [Normal              ] 24:     C ← "Phishing"

 516 [Normal              ] 8. RESULTS AND DISCUSSION
 517 [Normal              ] We compared our Graph Convolutional Network against two widely used baseline classifiers (Random Forest and XGBoost) trained on the same data using flat tabular features:
 520 [Normal              ] 8.1 Observations
 521 [List Paragraph      ] Handling Deceptive URLs: Baseline tabular models were often fooled by zero-day domains that looked realistic lexically (for example, chase-security-verify-login.com). The GCN correctly identified these links because it looked beyond the string: the domain was registered only three days prior, pointed to an untrusted IP range, and had mismatched SSL issuer details.
 522 [List Paragraph      ] Detecting Hijacked Sites: Sometimes attackers compromise old, legitimate websites and host phishing folders inside them. Lexical models often miss these because the root domain has an established age. Our GCN flagged several of these cases by detecting anomalies between the host IP and the SSL certificate issuer.
 523 [Normal (Web)        ] Addressing Network Bottlenecks: External WHOIS queries over port 43 cause major latency spikes, but adding an in-memory cache for common domains cut repeat scan times down to 0.25 seconds
 524 [Normal              ] 9. CONCLUSION, LIMITATIONS & FUTURE SCOPE
 525 [Normal              ] 9.1 Conclusion
 526 [Normal              ] In this project, we built a functional phishing detection system that uses Graph Neural Networks to analyze the infrastructure behind suspicious links[cite: 1]. By modeling relationships between URLs, IP addresses, nameservers, and registrars, our system learns behavioral patterns that bypass traditional blacklists and flat lexical classifiers.
 527 [Normal              ] Using PyTorch Geometric, NetworkX, and Flask, our model achieved a test accuracy of 96.85% and an average response time of 2.16 seconds, proving that graph learning can be practical, accurate, and fast enough for day-to-day web protection.
 528 [Normal              ] 9.2 Limitations
 529 [List Paragraph      ] Dependence on Third-Party Lookups: Because the system performs live DNS and WHOIS checks, rate limits or outages on external servers can slow down feature extraction.
 530 [List Paragraph      ] Proxy and CDN Masking: Cloudflare and similar CDNs sit between the user and the true server, masking the real hosting IP and nameserver behind generic proxy addresses.
 531 [List Paragraph      ] Ephemeral Single-Use Infrastructure: Attackers deploying links on free cloud hosting platforms (such as basic Firebase or Netlify subdomains) generate sparse graphs with minimal neighborhood context.
 532 [Normal              ] 9.3 Future Scope
 533 [List Paragraph      ] Graph Attention Networks (GAT): Upgrading the GCN to an attention-based model (like GAT or HAN) to automatically assign higher weights to critical relationships (such as nameserver changes) over less informative ones.
 534 [List Paragraph      ] Lightweight HTML Inspection: Adding quick checks for website favicons and page title tags into the node features to catch branded landing page spoofs.
 535 [List Paragraph      ] Browser Extension: Porting the client-side tool into a Chrome/Firefox extension that automatically checks links before the browser navigates to them.
 536 [List Paragraph      ] Continuous Updates: Building an automated worker script that pulls daily feeds from OpenPhish and PhishTank to periodically retrain the model against new attack trends.
